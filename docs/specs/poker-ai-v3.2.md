## 2. 首版玩法约定

### 2.1 固定参数

| 参数 | 首版约定 |
|---|---|
| 人数 | 固定 5 个座位：1 真人、4 电脑，各自竞争，不组队 |
| 初始筹码 | 每人 1,000，整数虚拟筹码 |
| 盲注 | SB 5、BB 10，固定不涨盲 |
| 其他强制费用 | 无前注、无抽水、无 straddle |
| 座位与位置 | seatId 不变；UTG、CO、BTN、SB、BB 根据当手按钮位置计算 |
| 首手按钮 | 随机确定；下一手按固定座位顺时针移动一位 |
| 手间节奏 | 结算后暂停，由用户点击“下一手” |
| 用户弃牌后 | 电脑继续打完本手，不立即跳到下一手 |
| 玩家行动时间 | 首版不设置真人行动倒计时 |

### 2.2 输光与补码

采用五人现金桌式练习玩法，不采用淘汰赛：

- 正在进行的一手内禁止补码。
- 结算后，非零余额全部保留。
- 开始下一手时，零筹码电脑自动补至 1,000。
- 真人为零时，“下一手”改为“补充 1,000 虚拟筹码并继续”；不操作则保持结算页。
- 五个座位都具备筹码后才开始下一手，固定五人位置轮换。
- 补码属于手间新增筹码，单独记为事件，不记作上一手赢钱。

例如结算余额为 `0 / 0 / 600 / 1,400 / 3,000`，真人选择补充并继续后变为 `1,000 / 1,000 / 600 / 1,400 / 3,000`。补码前后的总额变化必须能由补码事件解释。

### 2.3 一手流程

确定按钮和盲注位置 → 扣除盲注 → 洗牌发底牌 → 翻前 → 翻牌 → 转牌 → 河牌 → 摊牌或弃牌结束 → 结算 → 等待下一手。

短筹码不足盲注时按实际余额投入并全下，不借入筹码。即使大盲实际投入少于 10，正常翻前跟注基准仍为 10，首次完整加注至少至 20；筹码不足者仍可按规则短全下。已全下的大盲不再获得行动机会。规则状态应区分“规定的大盲额”和“实际已投入额”，不能仅用桌面最大投入推算最低跟注额。

洗牌使用服务端可靠随机源，测试可注入固定牌序；生产不接受客户端提供牌序或随机种子。

盲注先于发牌、固定现金桌盲注及基本流程参考 [PokerStars 规则](https://www.pokerstars.com/poker/games/rules/)。本项目的自动补码与手间暂停是明确的产品约定。

## 3. 规则引擎与金额协议

### 3.1 唯一裁决方

规则引擎负责发牌、合法动作、下注轮结束、底池资格、牌型比较及结算。前端和 DeepSeek 都只能提出操作，不能直接修改筹码、公共牌或底池。

选择开源引擎是第一阶段的技术验证任务，不能只因库名包含 poker 就认为它具备完整对局能力。需区分“牌型比较库”和“多人下注引擎”，核对许可证、运行环境及边界测试；缺失能力由适配层负责。选型报告要列出“库已覆盖 / 适配层补充 / 未满足”的能力清单，规则测试不过时不进入 AI 集成阶段。

### 3.2 动作契约

采用 `action + amountTo`，不再使用没有单位语义的 `amount`。

| action | amountTo | 服务端行为 |
|---|---|---|
| fold | null | 弃牌，保留已经投入的筹码 |
| check | null | 仅在无需补齐下注时合法 |
| call | null | 根据需跟注额与剩余筹码计算实际扣款 |
| bet | 正整数 | 本轮尚无下注时，投入至该累计金额 |
| raise | 正整数 | 将本轮累计投入提高至该金额 |
| all_in | null | 引擎计算投入全部余额后的累计额及其规则性质 |

例如大盲已经投入 10，`raise amountTo=30` 只再扣 20。`all_in` 可能构成跟注、完整加注或不完整加注，不能统一当作重新开放加注。

状态接口返回当前行动者的 `legalActions`、`toCall`、`minBetTo`、`minRaiseTo`、`maxTo`，以及是否只能以短全下形式超出当前下注额。不存在的动作范围返回 null。普通下注/加注和特殊短全下分别校验，不将不合法金额自动“夹到”另一个金额。

所有金额使用整数，并设置安全整数范围校验。底池金额的口径包含已经投入但尚未结算的各轮筹码，避免当前轮下注重复计入。

### 3.3 必须覆盖的规则

- 翻前从 UTG 开始，翻后从按钮左侧首个可行动者开始。
- 翻前全员跟注后，尚未全下的大盲仍有过牌或加注机会。
- 弃牌、全下玩家跳过行动；全下玩家仍可参与其有资格的底池。
- 下注轮结束不能仅看“所有人的投入相等”，还要确认必要行动已经完成。
- 一人全下不代表立即发完公共牌；仍有其他玩家可互相下注时继续处理边池行动。
- 只剩一人未弃牌时立即结束；未获跟注的筹码退回。
- 主池和每个边池独立确定参与资格与胜者；弃牌者投入仍在池内，但失去分池资格。
- 完整加注、不完整全下、累计短加注的加注权按行动者分别计算。
- 比较最佳五张牌，覆盖 A2345、踢脚、公共牌作为最佳牌等情况。
- 每个底池平分后不足整除的零头，按按钮左侧起顺时针顺序分给该池平局获胜者。

短全下与重新开放加注采用 [Poker TDA 2026 第 45、49 条](https://www.pokertda.com/view-poker-tda-rules/)作为实现参考；只引用适用的下注规则，不引入锦标赛淘汰、涨盲或重入制度。

### 3.4 筹码与隐藏信息约定

每手内保持“玩家剩余筹码 + 尚未派发的全部投入 = 本手起始总筹码”；结算后总额不变。补码只发生在两手之间。

多人桌不显示一个无对象的“有效筹码”。如果展示，则标明目标玩家，并采用双方本手起始筹码较小值；跟注额、当前余额和可竞争底池另算。

首版不生成精确胜率、GTO 频率或 EV。输入模型的确定性信息以跟注成本、下注与底池比例为主；如实现底池赔率，必须按该玩家实际有资格竞争的底池计算，并标明它不是胜率。

## 4. 状态模型与信息隔离

### 4.1 核心对象

| 对象 | 主要字段及职责 |
|---|---|
| GameSession | ownerId、gameId、stateVersion、aiEpoch、AI 模式、空闲过期时间 |
| HandState | handId、street、buttonSeat、actorId、turnId、牌堆、公共牌、投注与底池状态 |
| PlayerState | playerId、seatId、余额、当前轮投入、本手投入、folded/allIn、私有底牌 |
| ActionEvent | eventId、handId、turnId、执行者、最终动作、amountTo、实际扣款、执行来源 |
| PendingDecision | decisionId、actorId、预期版本、aiEpoch、开始时间、截止时间；不包含 Key |
| PublicInsight | actionEventId、公开解读、生成方式；不包含内部 reason 或私有意图判断 |

首版只保留当前手及结算画面所需的数据，不建设历史复盘或用户统计系统。

### 4.2 四种视图

| 视图 | 允许内容 | 禁止内容 |
|---|---|---|
| 完整引擎状态 | 全部牌和规则状态 | 仅限后端内部使用 |
| 真人可见状态 | 自己底牌、公共牌、公开动作、筹码、允许公开的摊牌结果 | 对手未公开底牌、剩余牌堆、内部决策文本 |
| 单个机器人决策视图 | 该机器人自己的底牌、公开信息、自己的牌风配置 | 其他玩家底牌、其他机器人私有推断、剩余牌堆 |
| 公开行动解读视图 | 截止目标动作时的公共牌、公开投入、位置、执行动作 | 所有未公开底牌、内部 reason、模型私有置信度与意图标签 |

在服务端构造专门 DTO，禁止直接序列化完整 GameSession 后由前端隐藏字段。RSC 数据、网络响应和错误信息都不得夹带完整引擎状态。

首版摊牌展示约定：实际进入摊牌的未弃牌玩家亮牌，已弃牌者不亮牌；仅靠其他人弃牌获胜不自动亮底牌。全下自动发牌时，在统一摊牌阶段展示结果。这是首版展示策略，不是承诺模拟所有现场亮牌与弃牌规则。

## 5. DeepSeek 决策协议

### 5.1 模型配置

- 官方地址固定为 `https://api.deepseek.com`，客户端不能自选代理目的地。
- 模型名为 `deepseek-flash`，集中配置；记录所用配置与提示词版本便于回归。
- 实时出牌首版建议显式关闭思考模式，返回简短 JSON。
- 建议初始参数：单次输出上限 800 tokens，单节点总等待预算 12 秒；属于待实测调优的产品默认值，不是性能承诺。
- 400/401/402 等不盲重试；429 或暂时性服务错误最多重试一次，且仍受总等待预算约束。
- 首版不请求模型联网、执行工具或计算整场最优策略。

截至核查日，官方文档确认模型名为 `deepseek-flash`，默认开启思考模式，因此模式应显式设置。[模型说明](https://api-docs.deepseek.com/quick_start/pricing/) · [思考模式说明](https://api-docs.deepseek.com/guides/thinking_mode/)

### 5.2 何时调用

有可用 Key 且处于智能模式时，每个需要机器人作选择的行动节点均调用模型。已弃牌、已全下、自动发公共牌、自动结算等机械步骤不调用。

禁止把“简单节点”作为未定义的绕过条件，让四名机器人长期由规则策略决定而只让模型补解释。首版先保证模型决策链真实有效，再用实测数据决定是否优化调用频率。

同一桌只能按行动顺序串行决策；后一个机器人必须看到前一个已经执行的动作，不能并行生成四个人的整轮策略。

### 5.3 四种牌风

| 角色 | 提示词中的行为倾向 |
|---|---|
| AI-1 紧弱型 | 起手参与较保守，面对明显压力更容易退出 |
| AI-2 松凶型 | 参与范围较宽，更主动下注与施压，但仍考虑筹码和位置 |
| AI-3 相对均衡型 | 综合位置、成本、牌面与公开下注过程选择行动 |
| AI-4 观察适应型 | 根据当前手已经发生的公开动作调整判断 |

AI-4 的适应范围明确限定为当前手，不宣称具有跨手学习或长期玩家画像。四名机器人互不共享私有上下文；牌风影响模型建议，不赋予超出规则的权限。

### 5.4 输入与输出

输入包括：当前行动者及牌风、自身底牌、公共牌、位置、各玩家公开余额与投入、主/边池信息、当前手公开动作历史、合法动作与金额边界。

输出示意（协议示例，不是程序实现）：

```json
{
  "action": "raise",
  "amountTo": 100,
  "opponentIntents": [
    {
      "targetPlayerId": "human",
      "hypothesis": "此前小额下注可能在试探，但也可能是价值下注",
      "confidenceLabel": "low"
    }
  ],
  "decisionSummary": "基于自身手牌、位置和公开下注过程作出的简短决策摘要",
  "confidenceLabel": "medium"
}
```

- 行动者由服务端当前回合绑定，不由模型或客户端指定。
- `amountTo` 仅用于 bet/raise；其他动作为 null。
- `opponentIntents` 必须带目标 ID，只能引用合法的其他玩家。
- `decisionSummary` 为私有简短摘要，不要求或展示模型内部推理链。
- `confidenceLabel` 为模型自评标签，不是经过校准的概率，也不作为自动通过校验的依据。
- 私有摘要和意图判断仅在当前请求处理所需范围使用，不进入公开状态或普通日志。

JSON 解析成功后仍需校验字段、长度、枚举、目标对象、金额与当时规则。空内容、截断和非法字段均走明确失败路径。官方 JSON Output 文档也提示可能返回空内容或被输出上限截断。[JSON Output](https://api-docs.deepseek.com/guides/json_mode/)

### 5.5 降级与真实 AI 验收

无 Key、不可用 Key、超时或非法模型结果时使用本地基础策略。安全兜底优先合法过牌，否则弃牌；不凭空生成非法跟注或任意改写模型金额。

每次最终动作记录来源：`deepseek`、`local_no_key`、`local_fallback` 或 `forced`。界面在降级时显示简短状态，不能持续显示“智能决策中”掩盖回退。

验收使用可控模型替身：对同一个允许过牌与下注的局面，分别返回两个合法结果，游戏必须分别执行对应结果；四个 seat 都需覆盖。真实 API 联调另外抽样验证，不靠“生成了一段解释”证明 AI 已经参与决策。

## 6. “AI 思路”改为公开行动解读

保留头像旁的“思路”入口，面板注明：**“基于公开信息的行动解读，不代表真实手牌或完整内部决策理由。”**

这是 V3.1 最重要的语义调整：机器人真实决策使用自己的底牌，而公开说明不能泄露该信息。把原始 reason 删掉牌名仍不安全，例如“我在诈唬”或“我有足够强的价值牌”也泄露了私有决策。

首版建议使用独立的公开解释模板，输入只接受 PublicInsightView 与已提交 ActionEvent，不读取私有 reason，也不额外增加模型调用。说明动作造成的公开效果及可能解释，避免伪装成机器人真实自述。

示例：

> AI-2 加注至 100，提高了其他玩家继续跟注的成本。这个动作可能出于价值下注或施压，公开信息不足以确定其真实牌力。

如后续要更丰富的文字，再以相同公开视图单独调用模型，不复用私有决策会话。该增强不作为首版必需项。

具体要求：

- 每名机器人显示本手最近一次已经提交的动作。
- 解读绑定 actionEventId，附动作发生的街道和金额。
- 使用动作发生当时的信息快照，不用后续公共牌解释之前的动作。
- 尚未行动显示“暂无行动”；进入下一手清空旧解读。
- 被拒绝、超时或取消的模型建议不产生已执行动作说明。
- 普通策略和 DeepSeek 策略都使用同一公开解释边界。

## 7. 机器人调度、版本与并发

### 7.1 请求驱动的连续回合

服务端不保存 Key，因此由浏览器驱动机器人行动：

1. 获取玩家可见状态，判断下一行动者。
2. 若为电脑且无在途决策，向决策接口提交 gameId、handId、turnId、expectedVersion、requestId；智能模式按需附带当前 Key。
3. 服务端验证匿名会话归属与行动状态，预留本回合决策名额。
4. 服务端构造该电脑视图，调用 DeepSeek 或本地策略。
5. 返回后再次检查版本和 aiEpoch，通过后才提交动作。
6. 浏览器取得新状态，按新回合继续请求，直到轮到真人或本手结束。

前端只触发“推进当前电脑回合”，不提交电脑的候选动作、底牌、牌堆或任意提示词。没有 Key 时通过同一流程运行本地机器人。

### 7.2 原子提交与幂等

- 同桌至多一个有效机器人逻辑决策流程，不同桌可独立处理。流程内的有限重试按独立上游尝试计数，不能把一次逻辑决策等同于只产生一次费用。
- 预留和提交在短临界区完成；等待远程模型时不持有阻止停用操作的长锁。
- 同一个 requestId、同一请求内容重复提交时返回原状态/结果；相同 ID 携带不同内容应拒绝。
- 即使换 requestId，同一回合的重复触发也不能创建额外逻辑决策流程。流程内重试按顺序发起；本地超时或取消不证明上游已经停止计算，因此不承诺供应商侧绝对不存在重叠处理。
- 所有修改都检查 handId、turnId、stateVersion；过期请求返回冲突与最新可见状态。
- PendingDecision 必须有截止时间。超时或取消要结束流程并释放名额，不能永久卡桌。释放前必须匹配原 decisionId，旧请求不得清除新 epoch 已预留的决策；结束后的旧响应不能再提交动作。
- 已经提交的动作不会因为客户端断线或没有收到响应而再执行一次。

### 7.3 刷新、离开、清除和更换 Key

- 刷新先读取服务器状态；已有在途决策时等待结果或截止，不直接重新付费调用。
- 页面关闭后不继续创建新的模型请求；已发送请求可能仍完成或产生费用，不承诺立即撤销。
- 清除 Key 时立即移除浏览器存储、停止新调度，再通知服务端停用 AI、提升 aiEpoch 并使旧的未提交决策失效。
- 更换 Key 时同样先停止旧调度，并通过 mode 接口提交 rotate 操作；即使仍是启用状态也必须推进 aiEpoch。新 Key 从服务端确认的新 epoch 开始用于后续请求。同一 requestId 重试不能重复推进 epoch。
- 以服务端确认停用/换代为生效点：此前已提交动作保留；此后旧 epoch 的结果不再提交。
- 若通知因断网未确认，页面显示“本地已清除，服务端停用尚未确认”；恢复连接后先同步状态。若停用遇到版本冲突，保持本地停用意图，同步最新版本后用新的 requestId 完成停用，不能静默恢复 AI 调度。
- 若当前标签页没有 Key，但恢复到服务器仍启用 AI 的牌桌，先停用并同步模式，再运行基础策略，不把缺少凭据的请求伪装成智能调用。
- 最佳努力取消上游请求，但不把客户端取消等同于供应商停止生成或免费。[MDN AbortController](https://developer.mozilla.org/en-US/docs/Web/API/AbortController/abort)只定义客户端异步操作的取消能力，不提供上游计费承诺。

## 8. BYOK 与会话约定

### 8.1 保留 sessionStorage 默认方案

沿用 V3.1 的取舍：刷新后不用重填，浏览器恢复会话时可能恢复 Key。不要将“网页不再保存”表述为“DeepSeek 平台密钥被吊销”。sessionStorage 的刷新与恢复行为见 [MDN](https://developer.mozilla.org/en-US/docs/Web/API/Window/sessionStorage)。

建议页面文案：

> 填写你自己的 DeepSeek API Key 可启用智能对手，调用费用由你的 DeepSeek 账户承担。Key 保存在当前标签页会话中，并在调用时经本站服务器转发；本站不持久化保存。正常关闭标签页通常会清除，但浏览器恢复会话时可能恢复。你可以随时清除本网页中的 Key；此操作不会注销 DeepSeek 平台上的密钥。

如果最终要求变为“刷新或恢复时也必须重新输入”，应将默认存储直接改为内存模式，而不是继续给 sessionStorage 作更强承诺。首版无需同时建设两个配置模式。

### 8.2 操作与状态

- “临时保存并测试”只在用户点击时调用测试接口，明确可能产生少量 token 费用。
- 不在输入过程中、每次刷新或每个组件渲染时自动测试连接。
- 状态区分：未配置、正在测试、可用、Key 无效、余额不足、限流、暂时不可用、已切换基础策略。
- 测试成功只代表该次请求成功，不保证后续请求一定可用。
- 清除动作覆盖 sessionStorage、组件状态、输入框和待重试请求中的引用。
- 浏览器禁止 sessionStorage 时临时使用页面内存，并提示刷新后需重填。

### 8.3 服务端使用边界

Key 只存在本次模型请求所需的请求作用域内，不写游戏 Session、全局客户端实例、队列载荷或缓存。避免共享客户端的 apiKey 被不同用户请求互相覆盖。请求结束后释放应用引用；不宣称 JavaScript 能证明物理内存已被覆盖擦除。

明确脱敏范围包括应用日志、代理访问日志、异常对象、链路追踪、客户端错误上报和请求重放工具。禁止记录含 Key 的完整请求头、请求体或 SDK 配置对象。提示词和原始响应也不进入公开日志。

HTTP 请求与响应禁止缓存；Key 不放 URL，不进入 NEXT_PUBLIC_*，不进入页面状态响应。生产 HTTPS、同源访问、请求大小限制、频率限制、CSP 和文本安全渲染保留。

### 8.4 费用信息

显示当前会话的请求次数、成功次数、降级状态；有 usage 的请求累计实际 token，用量缺失标为“未确认”。连接测试和自动重试均计入调用记录。

不按“一局只调用四次”估算费用；同一机器人可能在同一下注轮多次行动。首版无需给出精确人民币账单或加入付费管理系统。

## 9. 服务端部署与匿名会话

保留 Next.js + React + TypeScript + Tailwind CSS + Vitest。建议增加少量浏览器端验收，不能只用服务层单元测试证明 sessionStorage、刷新和网络请求符合要求。

首版部署约定：**单实例、单 Node.js 进程、常驻服务，游戏 Session 保存在该进程内存中。** 不将这份设计直接部署成依赖进程间共享状态的 Serverless、多进程或多副本服务。

刷新恢复仅在原进程存活且 Session 未过期时成立；重启、发布或内存丢失后返回 SESSION_EXPIRED，页面提示重新开桌。跨重启恢复或水平扩容属于另一个架构要求，届时才增加共享存储。这里是由内存存储方案作出的架构判断；Next.js 官方也说明各实例的进程内存各自独立。[Next.js 自托管指南](https://nextjs.org/docs/app/guides/self-hosting)

匿名不等于无鉴权：

- 服务端发放不可猜测的匿名访问者凭据，通过 HttpOnly、Secure、SameSite Cookie 关联 ownerId；Cookie 中不存 DeepSeek Key。
- 每张桌绑定 ownerId，所有接口包括 state 与 insight 都验证归属；gameId 本身不是访问授权。
- 写接口校验同源请求并提供必要的 CSRF 防护。
- 同一用户多个标签访问同一张桌时，仍执行回合版本与幂等规则，不重复推进。
- Session 设置可配置的空闲过期时间，建议初值 30 分钟，并限制总会话数量与请求速率；上线前按部署资源验证容量。
- 状态接口只返回白名单 DTO，并明确 no-store。

首版无需引入数据库、Redis、消息队列、微服务或 WebSocket。普通请求响应足以推进这类单人桌；在途状态可短暂轮询，不应高频持续刷新整桌。

## 10. 接口细化

所有写接口使用 requestId；涉及牌局修改时带 expectedVersion，服务端检查 ownerId。Key 只随 test 或需要 DeepSeek 的 decision 请求传递，使用专门且明确脱敏的请求头；不写在 URL 或公开请求模型中。

| 接口 | 输入与约束 | 输出 |
|---|---|---|
| POST /api/game/start | 创建或明确重开；requestId；重开使旧桌在途决策失效 | gameId、玩家可见初始状态 |
| GET /api/game/state | gameId；校验所有者 | 可见状态、版本、当前行动者、在途状态；不触发模型 |
| POST /api/game/action | gameId、handId、turnId、expectedVersion、requestId、action、amountTo | 已提交动作与最新可见状态 |
| POST /api/game/next | 仅已结算时；版本与 requestId；真人为零时显式携带补码选择 | 补码事件、新一手可见状态 |
| POST /api/ai/test | 用户主动触发；本请求 Key；限制频率 | 可用性分类、usage（若有），不返回 Key |
| POST /api/ai/mode | gameId、expectedVersion、requestId、operation（enable/disable/rotate）；不传 Key。rotate 在保持启用时也推进 epoch | 新 aiEpoch、模式及当前状态 |
| POST /api/ai/decision | 当前回合标识、版本、requestId、aiEpoch；按需带 Key | 本次已提交结果，或 pending/stale/错误状态 |
| GET /api/ai/insight | gameId、handId、目标 actionEventId；校验所有者 | 与已提交动作绑定的公开说明；不触发模型 |

`/api/ai/mode` 是新增的小接口，用于解决清除/更换 Key 对在途决策的控制问题；服务端只保存非敏感模式与 epoch。

业务错误统一区分：SESSION_EXPIRED、NOT_YOUR_TURN、STALE_STATE、DECISION_PENDING、INVALID_ACTION、KEY_INVALID、INSUFFICIENT_BALANCE、RATE_LIMITED、UPSTREAM_UNAVAILABLE。对冲突先同步状态，不将所有错误都自动重试。

## 11. 模块与开发顺序

目录保留 V3.1 的骨架，主要收紧职责：

- game-engine：完整规则状态与纯规则操作。
- session：所有者、过期、版本、决策预留与幂等记录。
- bot-strategy：无 Key 策略、牌风配置与兜底策略。
- decision-service：模型输入视图、输出校验、超时、epoch 检查和动作提交。
- deepseek-proxy：固定上游地址、每请求客户端/凭据、超时与错误分类。
- public-insight：仅接收公开视图和已执行动作，不能引用私有决策模块。
- components：牌桌展示、合法动作输入、Key 设置与公开解读。

| 阶段 | 开发内容 | 进入下一阶段的条件 |
|---|---|---|
| A 规则与契约 | 引擎选型、金额语义、补码、视图 DTO、固定规则样例 | 核心规则案例通过，缺失能力已有明确归属 |
| B 可玩牌桌 | 五座位、基础机器人、动作记录、手间结算、会话生命周期 | 不用 Key 可连续游玩，筹码守恒，刷新边界正确 |
| C BYOK 与调度 | sessionStorage、匿名所有权、请求脱敏、test、mode、pending 与幂等 | 不串用户 Key、不重复调用、可处理清除/刷新 |
| D 模型决策 | 四牌风、逐回合调用、JSON 校验、回退、调用来源与用量 | 模型替身测试证明四个机器人实际接受模型决策 |
| E 公开解读与发布验收 | 公开模板、移动布局、浏览器生命周期检查、部署说明 | 下列验收矩阵通过，真实 API 另行少量联调 |

安全和规则验收分阶段执行，不积压到最后才发现需要改架构。本文不估算开发天数；工期取决于规则库验证结果、现有代码与部署条件。
