# Poker AI — 给 DeepSeek 的开发交接说明与分阶段指令

日期：2026-10-22  
配套总规范：Poker-AI-V3.2-development-outline.md  
用途：指导另一个开发助手理解需求、分阶段实现和提供验证证据。本文件不是已经执行过的开发计划，也不表示任何功能已经实现。

## 1. 建议怎么交给 DeepSeek

先将 V3.2 全文作为总规范提供，再每轮下发一个阶段任务。完整需求让它知道模块之间的约束；当前阶段任务限定本轮要交付的结果。

不要仅按“先画页面、再加 AI、最后修规则”拆分。推荐顺序为：开工计划 → A 规则与契约 → B 无 Key 可玩牌桌 → C BYOK 与回合调度 → D 模型实际决策 → E 公开解读与整体验收。

每个阶段内部由它连续完成实现、测试、修复，不需要每个函数都征求确认。阶段结束时统一检查交付物，再发下一阶段指令。阶段较大时，拆成可以独立验收的小任务，不要求一条回复装下整阶段全部代码。

总规范里的 DeepSeek Flash 指游戏运行时的对手模型，不要求开发助手也必须采用同一个模型或相同思考模式。

## 2. 先确认开发环境能力

最好使用能够访问目标项目文件、修改代码并运行终端命令的开发环境。

如果当前使用方式只能聊天和展示代码，就由你把补丁写入项目、运行命令，再把实际错误返回给它；它必须明确哪些验证尚未执行。不能把“模型声称测试通过”当成本地验证结果。

DeepSeek 官方 Tool Calls 文档说明：工具函数由调用方提供和执行，模型本身不执行具体函数。因此能否改文件和运行测试，取决于承载模型的开发工具与授权，而不仅是模型名称。[官方说明](https://api-docs.deepseek.com/guides/tool_calls/)

将两份文档放进实际项目后，可按其现有约定存放；若没有文档目录约定，可使用：

- docs/specs/poker-ai-v3.2.md：经用户采用的总规范。
- docs/plans/implementation-plan.md：开发助手读取目标项目后制定的执行计划。
- docs/progress.md：阶段进度、验证结果、下一步和已知限制。

这些是交接给未来开发者的建议路径，本次没有创建实际代码项目。

## 3. 第一条消息：先理解与规划

发送这段提示词，并同时提供 V3.2 全文或可读取的文件：

```text
你将负责开发 Poker AI。附件《Poker AI V3.2 开发大纲》是本项目的总规范。请完整阅读，并按阶段交付。

先完成开工分析，本轮不开始业务实现：
1. 检查我指定的项目目录、现有代码和项目指令，保留已有修改；说明你是否能实际读写文件、执行命令和查看结果。
2. 用简短清单复述核心范围、规则边界、Key 生命周期、隐藏信息边界与明确不做的功能。区分规范已定事项和你的建议。
3. 对照规范制定 A—E 实施计划。每阶段写清产物、涉及的模块/接口、依赖、验证命令和对应验收编号；拆成可独立检查的小任务。
4. 第一项技术验证是规则引擎选型。最多比较两个合适候选，区分牌型比较与完整下注引擎，说明许可证、当前版本、资料来源、已确认能力及必须实测的缺口。不能编造库接口或声称未执行的测试已通过。
5. 明确项目需要的工具版本、包管理器和本地验证脚本。使用锁文件；已有项目沿用现有规范。Windows 下大型依赖和缓存优先放 F 盘，先检查复用已有工具，不恢复已停用的 Android 工具链。
6. 只提出真正影响实现且无法从规范确定的问题。若认为规范有冲突，指出原条款、影响和建议修订，不静默改范围。

本轮交付：需求理解、实施计划、规则引擎候选与验证方案、实际执行情况。完成后等我指定阶段。
```

检查它的第一轮答复时，重点看：是否先验证规则引擎、是否坚持服务端裁决、是否理解四个电脑必须实际接受模型决策，以及是否把阶段产物写成可验证结果。不要因计划长或目录多就认为它已经具备可执行性。

## 4. 全阶段通用执行要求

这些要求可放在项目指令文件中，或与每个阶段任务一起发送：

```text
执行当前阶段时：
- 先读取总规范、执行计划和当前进度，核对项目实际状态；仅完成当前阶段及其必要依赖。
- 在可操作的开发环境中直接修改项目文件，避免只在聊天中输出大量待手工拼接代码。
- 针对规则、状态转换、隔离和并发先建立有意义的失败案例，再实现并修复；不为凑数量写只复述实现的测试。
- 不自行新增账号、数据库、真人联机、锦标赛、历史复盘或 GTO 求解。调整协议前先说明影响，统一修改消费者与测试。
- 不用随机动作或固定返回冒充 DeepSeek 智能决策；测试替身仅用于明确的测试/开发路径，生产路径不能模拟连接成功。
- 保持每阶段可运行。定义并维护项目本地的测试、类型检查、lint、构建脚本，使用本地依赖与锁文件，不默认全局安装工具。
- 运行与改动相称的检查；阶段交付时执行约定的测试、类型检查、lint和构建。环境阻塞就报告准确原因，不声称通过。
- 模型接口先用测试替身验证。没有获准使用真实 Key 时，不进行付费调用；真实 Key 不放入聊天、提交文件、截图或日志。
- 在已有 Git 仓库中按有意义的任务保存本地提交；不覆盖已有改动，不擅自推送、部署或重写历史。
- 更新进度记录，列明本轮实现、验证证据、未实现事项与下一步，不把整个项目标成已完成。
```

推荐定义并保持可用的命令为 `npm test`、`npm run typecheck`、`npm run lint`、`npm run build`；若项目使用其他包管理器，统一换成其等价命令。实际脚本由开发助手根据目标仓库定义，不应机械运行不存在的命令。

## 5. 阶段 A：规则引擎和金额契约

```text
执行阶段 A：规则引擎与契约。

按已经审阅的实施计划，先用最小可运行的规则测试验证候选库，再确定采用范围与适配层职责。

本阶段产物：
1. 规则引擎适配、状态模型、action + amountTo 契约与合法动作查询。
2. 固定牌序测试入口，以及服务端随机源的生产边界。
3. 短全下、加注权、主池/边池资格、未跟注金额退回和结算的可运行测试。
4. 规则库的能力与缺口记录，引用实际安装版本及官方资料。

验收覆盖 V3.2 的 G01—G09、G11。G08 要分别覆盖弃牌结束与平局分池，G09 要覆盖列出的各类牌型比较，不能只写一个同名空壳测试。
重点核验 G02/G03 的不同加注权，以及 G04/G05 的底池和退款数值。

本阶段先形成能独立运行的规则模块和测试。完成后按统一交付模板汇报，未通过的规则不得带入下一阶段。
```

你应能看到：实际测试文件、执行命令、正确的数值断言和运行结果。仅有牌型比较库、界面截图或一句“支持边池”不足以完成此阶段。

## 6. 阶段 B：不使用 Key 的完整五人桌

```text
执行阶段 B：在阶段 A 已通过的引擎上，完成无 Key 可玩的五人桌。

本阶段产物：
1. 创建牌桌、玩家可见状态、真人动作、结算和下一手接口。
2. 五个固定座位、公共牌、行动记录、合法金额输入和筹码展示。
3. 四名基础策略机器人及浏览器按回合推进的流程；先实现 /api/ai/decision 的本地策略基础路径，阶段 C 在同一接口上完善 BYOK 与并发控制。
4. 匿名会话归属、单进程内存会话、空闲过期和刷新恢复边界。
5. 手间补码与真人弃牌后仍继续完成本手。

验收：保留阶段 A 的回归测试，补齐 G10、V03、S02 及 S01 对本阶段已有接口的归属检查；后续新接口继续补齐 S01。实际走通连续至少三手、真人提前弃牌、输光补码和刷新恢复；不能只展示静态牌桌。

先达到可正常游玩的界面，再进行视觉细调。记录启动方式、实际浏览器检查和仍未覆盖的情况。
```

这一阶段结束，你应该已经能玩一桌完整的普通机器人扑克。后面即使模型调用失败，也有稳定的基础玩法可回退。

## 7. 阶段 C：BYOK 与机器人回合调度

```text
执行阶段 C：实现 BYOK、模式切换和并发控制。

本阶段产物：
1. sessionStorage 临时 Key 设置、用户主动连接测试、清除与状态提示。
2. 固定 DeepSeek 上游地址的请求适配层；Key 仅限请求作用域，不进入 Session、全局客户端凭据、日志或缓存。
3. decision/mode 接口，含 enable、disable、rotate 和 aiEpoch。
4. requestId、handId、turnId、stateVersion、PendingDecision、截止时间与原子提交。
5. 刷新先同步，清除/更换使旧响应失效，同一回合重复触发不新建额外决策流程。

验收覆盖 A03、A04、K01、K03，并将 S01 的归属检查扩展到本阶段的新接口。使用可控的延迟、失败和并发测试替身；不依赖真实 Key 制造测试条件。
必须测试：清除 Key 时的在途响应、停用遇到版本冲突、同状态换 Key 仍推进 epoch、旧请求不能释放新 decisionId 的预留。

真实网络适配可以实现，但本轮不因测试而擅自调用付费服务。测试报告区分模拟验证与真实联调。
```

这一阶段不要只验收“输入框能保存 Key”。最重要的是两个用户不串 Key、双击不重复推进，以及停用后旧结果不再下注。

## 8. 阶段 D：四名 DeepSeek 对手实际决策

```text
执行阶段 D：把 DeepSeek 正式接入四名机器人的行动选择。

本阶段产物：
1. 每名机器人独立的信息视图、牌风配置和当前手公开行动历史。
2. 明确的非思考模式、输出预算、节点超时和有限重试。
3. JSON 结构校验、金额与合法动作校验、错误分类、本地降级。
4. 实际动作来源标记和请求次数/usage 统计；缺失用量标为未确认。
5. 服务器根据已执行动作更新状态，后一个机器人依据新状态继续决策。

验收覆盖 A01、A02、V01，并回归阶段 C 的在途与隔离测试。
对四个机器人分别注入至少两种不同合法模型结果，证明实际动作会随结果改变；不能仅增加一段模型解释。
替换其他玩家隐藏牌和剩余牌堆时，该机器人的输入必须不变。

先完成离线测试，再按用户指定的小额请求范围做真实联调；未提供 Key 或未进行联调时，明确记录“真实 API 未验证”。不能用模拟成功冒充已连通。
```

不要用“多玩几把感觉聪明了”替代这阶段的验收。可控结果能证明接入链路，真实联调用于确认 API 兼容性、延迟和实际返回。

## 9. 阶段 E：公开解读、浏览器验收与交付

```text
执行阶段 E：公开行动解读与完整交付验收。

本阶段产物：
1. 思路入口与“基于公开信息的行动解读”说明，绑定已经提交的 actionEventId。
2. 只使用动作发生时的公开视图生成说明，首版采用独立模板，不读取私有 reason。
3. 移动布局、下注操作和连接/降级状态的检查。
4. sessionStorage 的刷新、关闭与会话恢复实测记录。
5. 单实例常驻部署说明、启动说明、Key 与费用说明、当前限制。

验收覆盖 V02、K02，并按规范矩阵逐条说明23项验收场景的状态、对应测试或人工步骤与证据。
完成已约定的自动检查及浏览器走查；不能把构建成功等同于规则、隐私和真实模型调用全部通过。

交付可运行的代码和清晰的本地启动方式。公开部署作为单独的后续操作，不用部署占位页面替代本地验收。
```

## 10. 每个阶段结束时要求它这样汇报

```text
当前阶段：
实现内容：说明实际行为变化及对应文件。
规范覆盖：列出本阶段已覆盖的条款/验收编号。
验证结果：逐条列出实际命令、通过/失败/未运行，以及必要的输出摘要。
浏览器检查：说明实际走查的操作；没检查则明确未检查。
真实 API：是否调用、请求次数、可得的 usage；未调用则说明未联调。
已知问题：具体问题、影响范围、是否阻挡下一阶段。
进度记录/提交：进度文件位置；有本地 Git 提交则给出编号。
下一步：只说明紧接着的任务，不提前宣称整个项目完成。
```

阶段结束的判断是“产物可运行、关键行为可验证、证据与声明相符”，不以回复篇幅、文件数量或模型自评为准。

## 11. 失败、换对话和返修时怎么继续

遇到错误，把真实命令与报错交给它，限定修复范围：

```text
当前处于阶段［填写阶段］。下面是实际执行的命令和报错：
［粘贴命令与错误，去除密钥］

请先定位原因，做最小必要修复并复跑受影响检查。保留已经通过的功能与测试；不要为了通过而删除失败测试、跳过规则或重写整个项目。完成后按阶段交付模板说明修复和证据。
```

新开对话时提供：总规范、实施计划、最新进度、当前代码访问和失败日志。仅粘贴聊天摘要不足以可靠恢复代码状态。

```text
继续 Poker AI 项目。请读取总规范、实施计划、进度和现有代码，先核对实际状态。
目前要求推进阶段［填写阶段］；保留已有改动，不重新生成项目，不重复实现已完成部分。
若进度声明与实际代码或测试冲突，以实际结果为准并指出差异，再完成当前任务。
```

如果后续需要独立复核，提交当前差异、测试摘要和失败日志即可；无需发送真实 Key、完整凭据日志或重新讲述所有聊天历史。
